# Signed-in account security — decisions

Single-session policy: each successful password login now increments the user's auth version, deletes earlier sessions and creates the replacement session in one transaction. A later successful login invalidates previous devices/browsers on their next authenticated request. Failed passwords do not revoke the current session. Concurrent logins serialize; at most one token remains usable (a competing request may be rejected as credentials/session version changed). This applies to buyer, seller, delivery and admin. Same-browser tabs may share one token; hardware fingerprinting is not used. Already in-flight requests are not forcibly cancelled, and there is no push/socket logout notification. No existing real sessions are deleted by this implementation; policy takes effect as users log in again. This supersedes earlier multi-session login behaviour, while password/logout-all actions remain compatible.

Frontend follow-up: connected `/account` controls now call these endpoints, clear the local session on 204 and require fresh sign-in. See frontend `docs/ACCOUNT_SECURITY_UI.md`; earlier statements below that frontend controls were pending describe the backend-only checkpoint. No real user mutation was used to test the controls.

Implement authenticated password change and logout-all for all four roles. Both require current password and account-scoped throttling. Password change accepts a different 12–128 character password; no client user ID, role or session target is accepted. Changing password or signing out everywhere revokes every existing session, including the caller, and requires a fresh login. It does not reset identity/phone or claim SMS verification.

Use a user auth-version counter and matching session version, with legacy missing values interpreted as zero. Session creation and revocation serialize through the user document inside MongoDB transactions, preventing an old-password login racing revocation from issuing a usable session. Password verification/hashing happen outside transactions with a hash/version compare during the write. No raw password/token is logged or stored; responses are private/no-store. No real user account is altered by tests.

## Contract and limits

`POST /auth/password {currentPassword,newPassword}` and `POST /auth/logout-all {currentPassword}` require the existing Bearer session and return 204. All roles supported. Strict schemas reject client user IDs/roles and unknown fields. Passwords are 12–128 characters; unchanged password is rejected. Shared account-security throttle permits five attempts in each existing 15-minute bucket. Both operations revoke the caller and require a fresh login; no replacement token or recovery/password contents are returned. Other users remain unaffected.

User `authVersion` increments on successful security commands; matching versions are stored on sessions. Login transaction touches the user and compares the pre-verification hash/version before persisting a session. Password change checks the same hash/version before updating, incrementing the counter and deleting all sessions in one transaction. Existing legacy users/sessions without a counter behave as version zero; no migration or production user write is run by implementation.

Frontend integration remains pending; clients should clear their session after 204 and navigate to login. Forgot-password, phone/SMS ownership verification, lost-account recovery and MFA remain separate features, not fake endpoints. An already executing request authenticated before revocation may complete; revocation applies to subsequent authentication, not cancellation of in-flight business transactions.

Changed files: `src/auth/models.ts`, `src/auth/middleware.ts`, `src/auth/service.ts`, `src/auth/routes.ts`, integration tests and contract/docs. No real user password/session, `.env`, database infrastructure or live activation flag was changed. All security mutation tests use isolated users/database.
