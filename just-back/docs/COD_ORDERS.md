# COD order creation — decisions before implementation

User-confirmed launch policy (2026-10-29): COD first; online payments later. Product prices include tax; seller's configured listed delivery fee is final for seller delivery; pickup delivery fee is zero. No extra platform/service charge or promotional discount is applied. Unknown seller fees fail closed. Platform delivery remains blocked until dispatch capacity can be verified. These are application configuration decisions, not tax advice or accounting integration.

Implement `POST /orders` for authenticated buyers with `Idempotency-Key`, `{areaId,addressId,addressVersion,items:[{productId,variantId?,qty}],fulfilments:[{shopId,method}],expectedTotal,paymentMethod:"cod"}`. `expectedTotal` is an acceptance check only, never a price source. Client roles, shop ownership, line prices, stock, payment status and order status are rejected. All prices/fees and shop relationships are resolved server-side.

Within one replica-set transaction: resolve and revision-lock owned address/version; validate current browsing area; reserve all current listing SKUs; validate each shop minimum, selected method and active pincode service-area assignment; compute integer-paise totals; compare the accepted total; snapshot shop/product/variant/address identities and labels; create a placed COD order with unpaid status; mark its hold committed to that order. Failures roll back both stock and order. Committed holds cannot expire/release. No fake payment confirmation, rider assignment or delivery OTP is created.

Idempotency is buyer-scoped with deterministic document identity and canonical request fingerprint. Same-key/same-payload retries return the original order. Changed payload returns 409. Concurrent last-unit attempts serialize on products; order and hold commit atomically. Startup must verify the order reservation uniqueness index before production COD activation. `ORDERS_COD_ENABLED` defaults false until operator activation after integration checks; no real environment file is changed here.

Read APIs return only the buyer's own order DTOs and immutable order/address snapshots. Seller/admin lifecycle, cancellations and refunds need separate authorized transitions; order creation alone must not claim delivery operations are complete. Frontend should show a server-confirmed COD order only after success and preserve the bag on errors. Online payment methods return unavailable.

## Verified implementation — 2026-10-30

Final backend `npm run typecheck`, `npm run lint`, `npm run build` and `npm run test` passed. Full test result: **79 tests in four files**, using isolated local MongoMemoryReplSet. Earlier interrupted process results were unavailable, so checks were rerun rather than inferred. Existing Mongoose address-update deprecation warnings remain; no test failures occurred in the final run.

Eight COD tests cover default-off/auth/role/input gates, unpaid server-priced creation and same-key replay, committed stock immunity to expiry/release, immutable address/product snapshots, changed-payload conflicts, rollback after total/minimum/method errors, address ownership/version, delivery fee/coverage, concurrent duplicate and last-unit attempts, signed buyer-scoped pagination, foreign-order privacy, extra client prices/roles/payment methods, policy-correct read-only quote, and independent same-name/variant listings across two shops. All test fixtures and temporary account-role changes were confined to the isolated test database and cleaned up.

Changed backend files: new `src/orders/models.ts`, `service.ts`, `routes.ts`; shared-session support in `src/inventory/service.ts`; committed hold state in `src/inventory/models.ts`; address revision locking in `src/addresses/routes.ts`; COD configuration in `src/config/env.ts` and `.env.example`; route wiring in `src/app.ts`; policy-aware `src/cart/checkout-review.ts`; production index validation in `src/server.ts`; additive index declarations in `scripts/create-indexes.ts`; tests, README and API docs. The frontend change this phase is documentation in `docs/API_CONTRACT.md`; frontend application code is unchanged and frontend checks were not rerun.

`ORDERS_COD_ENABLED` remains false by default; no real `.env` flag was changed, no live order was placed, and no migration was run against Atlas. Customer-facing activation must wait for the frontend request/idempotent recovery/order-history integration and seller order processing. Online payment integration, cancellation/returns, COD collection/settlement and dispatch verification remain separate work. Production abuse control must also move beyond the current per-process order-attempt limiter when deploying multiple API instances.
