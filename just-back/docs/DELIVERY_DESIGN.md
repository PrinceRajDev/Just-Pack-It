# Platform delivery: implementation decisions and open policy

Inspection 2026-10-31: frontend delivery workspace is demo-only. Backend currently rejects platform_delivery placement, has no assignment domain and has no delivery cash ledger. Existing buyer receipt proof implements five-minute codes, attempt lockout and versioned completion; seller_delivery and pickup must remain intact.

Proposed lifecycle: ready shop suborder -> assignment to authorized active delivery-role account -> partner accepts -> seller confirms goods handover -> partner marks out_for_delivery -> buyer issues receipt code after receiving goods (and cash payment for COD) -> assigned partner verifies code and confirms exact frozen COD amount. Every command is versioned/transactional, with idempotent immediate retries and server-derived order/shop/partner/amount. No partner can self-declare delivered or reuse seller completion routes. Reassignment is only pre-pickup, invalidates old capabilities; after pickup use explicit operator exception handling, never silent reassignment or stock return.

Assignment identity is one shop suborder, not parent multi-shop order. Concurrent assignment claims require unique active suborder binding plus partner workload rule. History records actor/time/action and must not contain raw receipt codes. Distinguish cash collected by partner, cash remitted to operator and seller payout; neither one implies another or bank settlement. No invented payout/ETA/distance.

Privacy: only assigned partner receives minimal pickup/drop snapshot and contact data needed for active delivery; no buyer address in available/admin summary lists. Use consented contact details from owned account/saved order fields, not fake phone numbers. Navigation links use actual snapshot pins or encoded address, with clear external-map indication. No live GPS tracking is implied. Removed/foreign assignment returns404. Failed attempts and lockouts commit durably. Mask code/phone/address in logs.

Checkout enablement requires platform delivery coverage/fee policy, approved partner provisioning, service areas, dispatch availability rules and a disabled-by-default rollout switch. Existing shops must explicitly list platform_delivery. No production activation or .env modification occurs as part of implementation.

Pending user policy answers: admin assignment vs partner task claiming; listed seller delivery fee vs separate policy; COD buyer-code/partner-cash confirmation vs prepaid-only first. These decisions affect permissions, fees and cash obligations and must be resolved before dependent endpoints/placement are implemented.

Planned checks: cross-role/foreign-partner/foreign-shop denial; duplicate assignment race; stale version/reassignment; unpaid online cannot dispatch; seller pickup proof; invalid/expired/reused code and durable lockout; COD exact amount/duplicate confirmation; contact redaction; mixed-shop independent status; cancellation before/after dispatch; frontend loading/offline/reload and mobile keyboard states. All test orders and accounts isolated and clearly labelled.


Confirmed policy: partner claims available tasks; listed fee final, COD buyer receipt proof plus exact partner cash confirmation. Implementation uses one partner profile document as the transaction lock, activeTask pointer for one current task, embedded per-suborder assignment and order transaction for exclusive claiming. Claimable tasks are ready, live COD or captured live online, in approved partner active area coverage. Availability heartbeat expires after90seconds; dispatch rollout default false, no existing env activated. Seller confirms pickup before dispatch. Reassignment, post-pickup failure/cash remittance are explicit future operator exception flows; current active task cannot be silently released/reassigned. No cash-remittance or payout claim. Admin profile management binds existing active delivery-role accounts to areas, never changes buyer/seller roles. Available lists have signed user/profile-version cursors and no customer details; active details/contact are owner-only. Contact reads expose current account phones on explicit action; phone verification is not asserted. Checkout requires address/shop pins and6km+pincode coverage and at least one available approved partner; availability is not a reserved rider guarantee. Ready orders may wait for claiming.
