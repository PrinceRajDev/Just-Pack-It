# Signup email OTP

Follow-up: recovery reuses sending limits but uses distinct `purpose=recovery` challenges, bound user ID/authVersion, and dedicated recovery endpoints. Signup proofs are `purpose=signup`; pre-purpose outstanding codes must be requested again after upgrade. See MARKETPLACE_FOLLOWUP.md and frontend API_CONTRACT.md. Recovery sends use different email subject/copy and generic request outcomes; no existing unverified email/phone account is automatically linked.

Six-digit random email OTP verifies mailbox access, not phone/person/shop identity. Signup remains password-based; no email-code login or account linking. Require email OTP for new buyer/seller public registration by default. Existing accounts, operator provisioning and password login are unchanged. No account exists until the OTP is consumed inside the user/shop creation transaction. Unique verified email prevents reuse across accounts. A failed shop transaction leaves the OTP usable; a committed signup consumes it once.

Store only a keyed digest of the code; ten-minute expiry, five verification attempts, sixty-second resend cooldown, three sends per email per fifteen minutes, ten sends per IP per fifteen minutes. Default global limit is 200 send requests per UTC day (configurable 1–300), counted conservatively including failures/cooldown requests. Resend invalidates older codes. Use cryptographic randomness and private/no-store responses; never log or return OTPs. Provider acceptance is not proof of inbox delivery. Missing configuration disables new signup clearly, never bypasses verification or shows fake success.

## Brevo configuration

Use HTTPS `POST https://api.brevo.com/v3/smtp/email`, API key header, fixed text-only signup message and a verified sender. Only HTTP201 with a messageId is accepted. No automatic provider retries on ambiguous network failure; the code is invalidated and the user can request a fresh one after cooldown. Response bodies/provider errors and codes are never exposed/logged. Fifteen-second provider timeout, no redirects. No SMTP dependency, ports or Gmail App Password: compatible with Render's free-service SMTP-port restriction, subject to Render/Brevo account limits and availability. Actual hosting has not been tested or changed.

Backend `.env` (local and later Render environment): `EMAIL_OTP_REQUIRED=true`, `EMAIL_OTP_SECRET` (independently generated random secret), `BREVO_API_KEY`, `EMAIL_FROM` (verified/approved Brevo sender). Optional `EMAIL_OTP_DAILY_LIMIT=200`. The local secret/required flag are already prepared. No real provider key is shipped in `.env.example`; do not put any of these secrets in frontend Vite variables. Brevo sender/domain verification, transactional approval and remaining shared quota must be checked in the provider dashboard. Do not assume an arbitrary Gmail address is an approved sender.

## Contract

`GET /auth/registration-options` → `{emailOtpRequired,emailOtpAvailable}`. `POST /auth/email-otp/send {email}` →202 `{challengeId,expiresAt,resendAfterSeconds:60}`. This means provider submission, not delivery or verification. Registration payloads for `/auth/register` and `/auth/register/seller` add `email,emailChallengeId,emailOtp`. Required by default; admin/delivery cannot self-register. Missing proof400, expired/used/wrong/attempt-limited code400, resend/global limit429, unavailable configuration503, provider failure502. Existing SMS endpoints still fail unavailable. No client-supplied verified flag accepted.

`User.email` is normalized and unique when present; `emailVerifiedAt` is server-written. Challenge/cooldown TTL indexes and the partial unique User.email index must be included in the operator-reviewed `npm run db:indexes` before production rollout. Existing users without email are not marked verified. Legacy isolated QA explicitly opts out of OTP; new OTP tests use mocked Brevo and validate the mandatory path. No real mailbox delivery is claimed until credentials are configured and inbox receipt is checked.
