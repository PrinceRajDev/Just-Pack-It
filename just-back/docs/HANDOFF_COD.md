## Confirmed policy — 2026-10-30

The user approved buyer receipt code plus seller cash confirmation. Implement code issuance only after explicit buyer acknowledgements that goods were received and cash paid. Pickup must be ready; seller delivery must be out for delivery. Six random server-generated digits, five-minute lifetime, one issuance per 60 seconds, five wrong attempts then a 15-minute lock, and account-level issuance/verification throttles. Reissuing rotates the secret; a lost response requires waiting for a new code. Store only a context-bound HMAC using the backend session pepper (separate domain), never plaintext. Ordinary buyer/seller DTOs and logs must not expose code/hash/nonce.

Completion requires the current shop owner, expected version, code, explicit cash-received acknowledgement and amount matching the frozen server amount. Status becomes delivered and a buyer/seller cash report is written atomically; this is `cash_recorded`, not gateway-verified payment or settlement. Order totals stay immutable, outstanding COD excludes cancelled and recorded-cash suborders, and original cancelled amounts remain separate. Wrong-code counters must commit even though the API rejects the attempt. An immediate identical successful retry is idempotent; a used code cannot create another collection or transition. Suspended shop owners can complete already-happened handoffs with valid buyer proof, while dispatch still requires active approval. No platform rider flow, SMS integration, settlement, reversal or refunds are implied. Keep live ordering activation unchanged.

First independent step: a seller-delivery suborder may move `ready → out_for_delivery` through its current approved shop owner and expected version. Pickup cannot use that transition. Dispatch tracking is not a rider assignment, delivery confirmation or cash collection. Preparing/ready/dispatched cancellation stays unavailable pending exception/spoilage handling.

The user confirmed the completion policy: the authenticated buyer generates a short-lived receipt code only after receiving goods and paying cash; their shop's seller verifies that code with an explicit actual-cash-received declaration. No SMS provider or gateway verification is implied. Cash reports remain distinct from online payment settlement.

Any receipt secret must be server-generated, hashed with a backend secret and bound to order/suborder/buyer/version, short-lived, attempt-limited and single-use. Ordinary order/seller DTOs must not contain it. Cash amount comes from immutable server snapshots, never from client status or a trusted client amount. Completion, secret consumption and cash audit must share a transaction; retries must not create duplicate collections or restock sold goods. Missing/mismatched/expired proofs fail closed. Live COD activation stays off during this work.

## Receipt/cash implementation and verification — 2026-10-30

Implemented buyer-only `POST /orders/:orderId/suborders/:subId/receipt-code {version,confirmReceived:true,confirmCashPaid:true}` returns `{code,issuedAt,expiresAt,amount}` once with private no-store headers. Issuing does not change visible status/version or record collected cash. One-minute rotation cooldown, five-minute expiry and ownership/status/version checks apply. Regeneration avoids repeating the previous raw code and replaces the context-bound HMAC/nonce. Account issuance throttle is 20 requests per 15 minutes in MongoDB. No raw secret is stored, logged, returned by order reads or persisted by the frontend.

Seller-only `POST /seller/orders/:orderId/suborders/:subId/complete-cash {version,code,confirmCashReceived:true,amountReceived}` validates exact server cents and receipt proof. Verification throttle is 60 requests per authenticated seller per 15 minutes; five valid-format wrong codes lock that suborder for 15 minutes. Wrong counters commit before the API error, so retries cannot roll them back. Reissue is blocked during lockout. The buyer must issue a new code after expiry/unlock. Completion atomically consumes proof, creates one immutable cash report/audit event and marks delivered/version+1, without changing stock. Same original successful command can be replayed safely even after code expiry; any other reuse is rejected. Direct status PATCH cannot mark delivered or paid.

Public/private DTO payment states are `unpaid|partially_cash_recorded|cash_recorded`. The last two mean documented cash reports, never gateway/bank verification or platform settlement. Original checkout `total` remains immutable; `cashRecordedAmount` and remaining `amountDue` are separate from `cancelledAmount`. Each seller sees only their own suborder's cash state/amount, not other shops' collections or receipt secrets. Cash reports expose amount and timestamps; reporting actor IDs, hash/nonce/attempt metadata stay internal. Cancelling another unprepared shop after partial collection updates the aggregate correctly without cancelling/restocking the delivered shop.

Buyer UI requires both explicit receipt/cash acknowledgements, displays the returned code only in component memory and hides it at expiry or failed rotation. Seller UI requires six digits and actual-cash acknowledgement; wrong codes can be corrected, uncertain/expired/locked outcomes require refreshing server state. Ready pickup and dispatched seller delivery are supported. Completed views accurately label cash as recorded and do not offer a new receipt action. Existing order recovery accepts server cash-recorded replays of an original placement, preserving its immutable accepted total.
