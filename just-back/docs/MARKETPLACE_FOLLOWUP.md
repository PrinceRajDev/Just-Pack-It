# Four marketplace follow-ups — decisions before implementation

GPS address confirmation: GPS resolves shop discovery only; no reverse-geocoding guess. After an eligible service area is selected in GPS mode, prompt for house/street/landmark and confirm city/locality/pincode. Save through existing authenticated owned-address API only on explicit confirmation. GPS coordinates are not silently converted into a deliverable address, no external geocoder/paid service. Dismissal leaves browsing available; checkout still requires a valid saved address and server serviceability review.

Password recovery: a distinct email OTP purpose bound to an existing active user's verified email and current authVersion. Signup proofs cannot reset passwords or vice versa. Expiry, resend/guess/IP/global limits reuse existing email machinery. Reset consumes proof and changes password/revokes all sessions in a single transaction; races with password change/login invalidate stale proof. Generic recovery request response avoids confirming account existence. Missing Brevo fails unavailable; provider submission is not inbox delivery. Existing accounts without verified email cannot use email recovery. No automatic email linking based on client input.

Buyer cancellation: authenticated owner only, per shop suborder, before preparation (placed/accepted); prepaid capture must already be verified. Version checks and retries use existing order transition transaction; return stock once and create a requested refund obligation for captured online payments, never claim bank refund. Racing seller preparation wins or loses atomically. Cancellation after preparation, disputed handoffs and unpaid Razorpay closure are not introduced by this endpoint. Original totals/snapshots remain immutable; cancel reason/history and current amount due change per existing rules.

Admin operations: authenticated admin-only bounded summary of pending shop approvals, orders with an active suborder unchanged for60minutes and unresolved payment/refund operations. Stale means attention, not guaranteed delay/SLA breach. Counts from database, no fabricated metrics and no customer addresses, receipt codes, phone numbers or payment secrets. Actions link to existing approvals/orders/finance screens for review; no automatic approval/refund or delivery assignment.

## Implementation and remaining dependencies

All four features implemented. Existing auth/session model, frontend router, service-layer API access and image/payment providers retained. No new external service, paid API, production migration or deployment. Recovery uses configured Brevo HTTPS credentials but remains unavailable while the user's sender setup is paused. Actual mailbox receipt/provider availability must be checked later; unit/API tests use explicit provider doubles. Old users without `emailVerifiedAt` cannot reset via an unverified mailbox. Purpose-less outstanding signup codes from earlier versions must be requested again after upgrade.

Cancellation endpoint uses the existing transactional order/stock/refund transition engine without masquerading as a seller. Buyer identity is recorded in history, seller is notified, no cash record is fabricated. Original totals retained; current due/refund state is visible. Cancellation after preparation and unpaid online-order closure still require separate operations; no fake cancellation approval is returned.

GPS address prompt acknowledgement is kept with the transient GPS selection, so route navigation does not repeatedly reopen the sheet. It can be opened manually from the area banner. Full page reload intentionally clears precise GPS. Address fields are explicit and owner-scoped; labels/landmarks are not inferred from coordinates. The usual address-version/serviceability checks apply at checkout.

Operations dashboard replaces only connected admin home; the approvals workspace remains `/admin/partners`. Queues have counts and up to10 samples each, linking to existing review workspaces. Counts use separate bounded database reads, not one transactional snapshot; use Refresh operations to recheck before acting. Auto-refresh is every60seconds while active. No SLA, settlement or automatic payment/refund decision is implied.
