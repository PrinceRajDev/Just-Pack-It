# In-app notifications — design

Persist durable notifications alongside committed business transitions in the same MongoDB transaction, with deterministic event IDs so retries do not duplicate alerts. Scope recipients to a specific user or the admin role; no client controls recipient/body/link. Store per-user read receipts, including for shared admin alerts. Authorize list/count/read at the backend. Cursor pagination is signed and actor-scoped. Text contains no address, receipt OTP, credentials, raw provider response or other shop's private order data.

Buyer events: order creation, shop status/handoff, verified online capture, refund state. Seller: own COD new order, prepaid order after capture, own shop approval outcome. Admin: shop submissions, edited profiles needing re-review, and recovery-worker manual review alerts. Recovery alerts are separate from the recovery lease completion transaction and deduplicated by source record; worker errors remain visible in its existing logging. Existing old orders are not backfilled as fake new notifications. Delivery accounts have an honest empty inbox until platform delivery events are implemented. Notification polling while signed in is not Web Push, SMS, WhatsApp or email. Same warm UI and current router remain unchanged.

## API and operations

`GET /notifications` accepts strict limit (1–50, default20) and optional actor-scoped cursor, returns an array with `id,title,body,link,createdAt,read` and cursor headers. `GET /notifications/unread-count` returns `{count}`. `POST /notifications/:id/read {}` returns204; unrelated/missing IDs return404. Read receipts cannot be edited for another user. No public write API.

No additional credentials. Development uses existing auto-index configuration. Before a production rollout, an operator must run `npm run db:indexes` from the backend after reviewing the declared additions: Notification recipient/date/id and admin/date/id indexes; NotificationRead unique user/notification index. This task does not run an index migration against Atlas. Existing events are not retroactively imported. Notifications currently have no automatic retention/deletion policy; choose retention based on actual operations before sustained production traffic. Polling pauses in background tabs under the existing TanStack Query defaults; it is not guaranteed immediate delivery or a replacement for the order/payment source of truth.
