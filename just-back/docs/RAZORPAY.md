# Razorpay integration decisions

Background recovery follow-up: `PAYMENT_RECOVERY.md` documents a separate opt-in GET-only provider recheck worker for mapped pending payments/refunds. Default `PAYMENT_RECOVERY_WORKER_ENABLED=false`; it is not started by the API server and cannot initiate payments/refunds or release stock. Admin DTOs/views now expose sanitized recovery history and review warnings. Existing Razorpay activation requirements and actual-provider verification gaps remain unchanged.

Refund follow-up: seller pre-preparation prepaid cancellation now requests a shop-wise refund while atomically returning stock. Admin-confirmed normal refund submission/recovery, provider status verification and signed processed/failed refund events are implemented behind `RAZORPAY_REFUNDS_ENABLED=false`. This supersedes older statements below that all prepaid cancellation/refunds were blocked. See `REFUNDS.md` for exact scope and remaining exceptions. No actual provider refund was executed in implementation checks.

Admin operations follow-up: `/admin/finance` now provides paginated online payment inspection and reconciliation. See `PAYMENT_OPERATIONS.md` and frontend `docs/API_CONTRACT.md`. Mapping a missing provider order now requires `confirmProviderOrder:true` and a 3–300 character `reason` alongside the actual provider order ID. Existing `{}` rechecks remain compatible. Credentials were checked for presence only: none of the three Razorpay credentials were configured, and both activation flags remained off at this checkpoint. No provider request or live configuration change was made.

Server prices and reserves the complete multi-shop order using the existing transactional order builder. Online attempts are separate from COD idempotency identities. Sellers cannot process unpaid online orders. INR only; no partial payments, client-supplied paid state or client-controlled amount. Only a verified captured payment with matching provider order, amount and currency marks paid. Browser callback signatures use the server-stored provider order ID; raw-body webhook signatures use a separate secret. Duplicate/out-of-order notifications do not regress paid state or decrement stock again.

Provider creation happens outside MongoDB transactions. Persist a creation claim before making the external request. An uncertain create is not blindly repeated: reconciliation is required, preventing duplicate payable gateway orders. Payment callbacks/webhooks reconcile using the provider API. No external payment call is made by automated tests; provider responses are explicit test doubles only.

Unpaid online orders retain committed inventory. Modal dismissal/failure is not proof that capture cannot arrive later; never release that stock automatically or switch to COD. Monitor/reconcile abandoned attempts before production rollout. Seller cancellation of prepaid orders is blocked pending a refund workflow; no fake refund or settlement is recorded. Prepaid handoff verifies buyer receipt without asking for cash. Collection uses the platform Razorpay account; split seller settlement/Route integration is not implied.

Defaults keep online payments disabled. Backend-only credentials: `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`; `RAZORPAY_ENABLED=true` enables test integration when all credentials are configured. Live keys require an additional explicit `RAZORPAY_LIVE_ENABLED=true`. Do not activate live keys until refund/abandonment/reconciliation and marketplace collection/settlement arrangements have been reviewed. No credentials belong in frontend env files.

Test-key online orders persist `testMode:true` on the order and expose it to buyer, seller and admin DTOs. Every role sees a test-order warning: no real payment/purchase and no physical fulfilment. Test-mode `paid` means captured in the provider test environment only. Run test checkouts against staging/test shops: they still reserve that environment's real database inventory. No fake production shops/orders were created by this implementation.

Official references: https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/ ; https://razorpay.com/docs/webhooks/validate-test/ ; https://razorpay.com/docs/api/orders/create/ . Configure automatic capture in the Razorpay dashboard. Webhooks require a publicly reachable HTTPS URL; localhost alone cannot receive them.

## Setup (test mode first)

Configure the three credentials in `D:\justpackit\just-back\.env` only, set `RAZORPAY_ENABLED=true`, keep `RAZORPAY_LIVE_ENABLED=false`, then restart the backend. `RAZORPAY_KEY_ID` must start with `rzp_test_`. The webhook secret must be independently generated (at least 32 characters) and match the dashboard webhook configuration. Configure `POST <public-backend-url>/webhooks/razorpay` for `payment.captured` and `order.paid`. Never paste secrets into chat or frontend env. Dashboard automatic capture is required; authorized-only payments remain unpaid locally.

Create the declared indexes with the existing reviewed `npm run db:indexes` deployment process before enabling on production. This change does not run it against Atlas. Production startup verifies provider order/payment uniqueness and one-pending-online-order-per-buyer indexes. Do not use `syncIndexes`, destructive database cleanup or fake production seeds.

Buyer creates an online order from the checkout method selector, then opens Standard Checkout from its order detail. Payment status can be checked after reload or callback loss. Pending order creation can be recovered from account. Provider creation failures stay `uncertain` and require an operator; do not delete the attempt or free stock while a late capture is possible. Admin can use `POST /admin/payments/:marketplaceOrderId/reconcile {providerOrderId:"order_..."}` to bind an actually verified provider order by its matching receipt/amount/account and reconcile capture. If no provider order exists, or a refund/abandonment is required, operator-reviewed handling is still needed; there is no unsafe automatic release or refund claim.

The existing admin order monitor displays online method/status separately. Its outstanding/recorded cash filters apply only to COD orders; online unpaid orders appear under all orders. Amounts are not settlement balances. Notifications, seller payouts, Route split settlements, partial/full refund automation, chargeback handling and a safe unpaid-order closure workflow remain launch dependencies. Keep live activation off until these are resolved.

## Validation boundaries

Automated tests use an isolated MongoDB replica set and explicit provider HTTP test doubles; they never contact Razorpay or simulate successful payments in application/demo data. Test account credentials, a real test-mode Standard Checkout payment and public webhook delivery must be verified separately after credentials are configured. Test keys do not prove live KYC, payment-method activation or marketplace settlement readiness.

Current checks: backend 95 tests/four files and frontend 122 tests/26 files passed. Both TypeScript checks, lint and builds passed (frontend retains 22 existing Fast Refresh warnings). Tests cover signature rejection, exact amount checks, authorized versus captured status, replay/duplicate webhook handling, uncertain provider-create recovery without a second provider POST, one pending online order per buyer, hidden unpaid seller orders, refund-required cancellation, prepaid receipt without cash, callback dismissal, local attempt recovery and account changes. No live/test Razorpay API request or real gateway checkout was run during these checks.

Changed frontend: new online-payment domain/service, `OnlineOrderAction`, `OnlinePaymentPanel`, checkout review, account/order/seller/receipt views, payment/domain types and labels, COD attempt guard, admin cash labels, and payment/receipt/admin tests.
