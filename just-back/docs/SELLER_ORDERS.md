# Seller suborder processing — decisions before implementation

Current extension: seller delivery additionally supports ready→out_for_delivery, with the same ownership/version/approval checks. Pickup does not. This does not complete delivery or collect COD; see `HANDOFF_COD.md` for the verified dispatch work and pending receipt/cash policy decision.

Preserve COD unpaid status and immutable checkout/address/product snapshots. Seller sees only the suborder for the shop currently owned by their authenticated account. Never return the parent order's buyer ID, other shops' items/totals, request fingerprints, reservation identity or payment secrets. The saved delivery address is returned only for seller-delivery suborders; pickup does not expose it.

Allowed transitions: `placed → accepted → preparing → ready`. `placed → cancelled` is rejection; `accepted → cancelled` is pre-preparation cancellation. Cancellation requires a trimmed 3–500 character buyer-visible reason. Preparing/ready cancellation is blocked until category-specific spoilage/return rules and operational exception handling exist. No delivered transition, OTP, rider assignment or COD collection is fabricated.

Every mutation carries the suborder's current nonnegative `version`. A matching immediate retry (same from-version, target and reason) returns the saved result without writing twice. Stale or conflicting commands return 409. Transitions, actor/time history and version increments share a MongoDB transaction. Non-cancellation transitions require an active approved owned shop; an owner may reject/cancel pre-preparation orders even if the shop has since been suspended. Shop revision locking serializes approval/ownership decisions.

Cancellation validates the linked committed hold against this suborder's frozen SKU quantities and restores exactly those base/variant units in the same transaction as status/reason/restock marker. Other suborders remain committed. Repeated/concurrent cancellation cannot restock twice. Missing/corrupt inventory or mismatched hold data rolls back the whole cancellation for operator reconciliation, rather than silently losing stock. Soft-deactivated listings/variants can receive their stock back without being reactivated.

Original order/line/fee totals remain immutable for idempotent creation replay. Buyer DTOs additionally expose `amountDue` (non-cancelled suborders) and `cancelledAmount`; no payment/refund is claimed. Seller DTO totals contain only that seller's suborder. A cancelled suborder has zero COD amount due. Full committed holds never expire after partial cancellation; restock state belongs to each suborder.

APIs: seller-only `GET /seller/orders?limit&cursor&status`, signed owner/shop/filter-scoped cursor headers, returning flat shop-only suborder DTOs; `PATCH /seller/orders/:orderId/suborders/:suborderId {version,status,reason?}`. Private no-store responses. Mutations return one shop-only DTO. Existing demo workspaces remain unchanged. Live COD activation stays off pending dispatch/handoff, COD collection policy and end-to-end verification.

## Integration and verification — 2026-10-30

`/seller/orders` is now in the live seller navigation, with real filtered orders, forward-only processing buttons, required buyer-visible rejection reasons, success feedback and retry/empty/error states. Active approval is required to accept/prepare/mark ready, while safe pre-preparation rejection remains available to an owner of a suspended shop. Failed/uncertain mutations lock further actions until explicit reload; reloading resets the card from server state. The order screen does not depend on taxonomy/area requests succeeding. Buyer details show saved statuses/reasons, original total, current COD due and cancelled amount, with a refresh action; no real-time push is claimed.

Final backend `npm run typecheck`, `npm run lint`, `npm run build` passed; all **84 tests in four files** passed against isolated local MongoMemoryReplSet. Frontend `npx tsc --noEmit`, test/build/lint passed: **106 tests in 23 files**, zero lint errors and 22 existing Fast Refresh warnings. New/expanded tests cover seller roles/ownership, status sequencing and version conflicts/replays, pre-preparation cancellation only, exactly-once concurrent restocking, accept/cancel races, suspended-shop safety, corrupt hold rollback, inactive listing restock, shop/variant isolation in partial cancellation, signed cursor/filter/owner scopes, delivery-address privacy and customer totals. UI/service tests cover reason/approval gates, success feedback, retry recovery and snapshot/amount display.

An intermediate API test found a 500 caused by passing a hydrated embedded Mongoose document into the DTO mapper. Mapping the plain order snapshot fixed serialization and prevents leaking document internals; final response tests assert public line fields and absence of `_doc`. No real customer/shop/order transitions, COD collections, payments, explicit index migration or activation flag changes occurred. Populated browser end-to-end verification remains outstanding.

Backend files changed: `src/orders/models.ts`, new `src/orders/seller.ts`, `src/app.ts`, `test/phase1.test.ts`, and documentation. Frontend: new `src/domain/seller-orders.ts`, `src/services/seller-orders.ts`, `src/components/portal/LiveSellerOrders.tsx`, `src/test/seller-orders.test.tsx`; additive domain fields, live seller routing/navigation, buyer detail/history display, API adapter and buyer UI tests, plus documentation. Additive seller-list index is declared on the Order model and is included by the existing operator index workflow; it was not explicitly applied to Atlas here.
