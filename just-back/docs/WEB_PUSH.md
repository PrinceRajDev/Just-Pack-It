# Firebase web push

Design before implementation: explicit browser opt-in, no automatic permission prompt. Store one push registration per authenticated session with hashed registration-token ID, user, session and role. The existing single-session policy is authoritative. Never accept a recipient/role/message from the client. Registration tokens are private operational data.

Create delivery jobs in the same transaction as new in-app events, only for subscriptions already opted in at event time. A separate worker sends outside business transactions, claims jobs with leases, retries with a bounded backoff and expires old jobs. Validate account/session/token ownership immediately before each send. Never send order details, shop names, OTPs or amounts to lock screens: use generic text linking to the signed-in account. This reduces exposure if an already accepted provider message reaches a revoked device; provider-accepted pushes cannot be recalled. At-least-once processing can resend after a worker crash; use a stable notification tag. In-app records remain the source of truth.

No Firebase Auth, Analytics, Firestore, hosting or payment integration changes. Localhost testing is supported; public hosting requires HTTPS. Browser permission/support and OS settings determine delivery. No guarantee of delivery when a browser/OS is fully stopped. Credential validation and dry-run acceptance do not prove device delivery.

## Configuration and running

Backend `.env`: `FIREBASE_PUSH_ENABLED=true`, `FIREBASE_PROJECT_ID`, `GOOGLE_APPLICATION_CREDENTIALS` (absolute local JSON path). JSON stays in ignored `secrets/`, excluded by the Docker allowlist. `npm run check:firebase` checks OAuth credentials only, with no sends or database access. Never put this file/private key in Vite variables.

Frontend `.env.local`: public `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_MESSAGING_SENDER_ID`, `VITE_FIREBASE_APP_ID`, `VITE_FIREBASE_VAPID_KEY`. Analytics/storage config is unnecessary. Restart frontend/backend after environment changes. The supplied public web config has been configured locally; no credential JSON is copied into the frontend.

Run the API as usual, and separately from `just-back`: `npm run notifications:worker`. Production compiled command: `npm run notifications:worker:start`. Index setup is operator-reviewed `npm run db:indexes` (adds PushSubscription session-unique/TTL/user/role and PushJob due/retention indexes); production worker checks critical indexes. No Atlas index migration is run by this task. Jobs expire after one hour and are purged after seven days; provider TTL is sixty seconds. Five attempts with backoff; stale leases may be recovered after two minutes. No retrospective alerts or sending to a new login for an old login's job.

Open the signed-in notification bell → Enable browser alerts → allow the browser prompt. Permission is never requested automatically. Re-enable for each new login; logout/session expiry/another-device login prevents future worker sends to that old session. Disable removes the server registration even when browser token cleanup fails. Tokens are excluded from list/status responses and never logged. Existing provider-accepted generic alerts cannot be recalled.

`GET /notifications/push` → `{available,subscribed}`; `PUT /notifications/push {token}` →204; `DELETE /notifications/push` →204. All authenticated, private/no-store. Strict input, session-based recipient/role, bounded per-account registration throttle. Existing active token ownership cannot be taken over by another user. No arbitrary test/send endpoint. Device delivery requires a real opt-in subscription and running worker and remains separate from OAuth validation.

SDK: Firebase Admin on backend, lazy `firebase/app` and `firebase/messaging` web modules. The custom same-origin root service worker receives FCM data-only Web Push through the standard `push` event; it accepts only UUID event tags and renders fixed generic copy. Click destination is fixed `/account`. Visible windows refresh their inbox instead of generating duplicate system alerts. Firebase's umbrella package includes unused Firestore dependencies; gRPC is overridden to patched 1.13.6 because of GHSA-m9gg-hp2v-232j. Firestore and gRPC are not used by this browser flow. See https://github.com/advisories/GHSA-m9gg-hp2v-232j and https://firebase.google.com/docs/cloud-messaging/web/receive-messages.
