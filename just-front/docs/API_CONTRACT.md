## Google sign-in — 2026-11-01

`GET /auth/registration-options` adds optional `googleSignInAvailable`. With Firebase Google provider configured, the frontend obtains a Firebase ID token through a popup (memory-only client session) and calls `POST /auth/google {idToken,phone?,password?}`. Response is the existing `Session`; database role and single-device session rotation remain authoritative. Server checks the Firebase project, signature, expiry, revocation, Google provider, verified email and recent authentication. OAuth access tokens/client email claims are not accepted as proof.

409 `GOOGLE_ONBOARDING_REQUIRED` opens existing buyer/seller onboarding. Both registration endpoints accept `googleIdToken` instead of `emailChallengeId,emailOtp`; phone/password and seller shop fields remain required. Google email verification does not verify the phone or approve the shop. 409 `GOOGLE_LINK_REQUIRED` requires existing phone/password confirmation before binding Google to a matching verified-email account; matching email alone never signs into or links an existing account. Inactive, mismatching or unverified accounts fail closed. No admin/delivery self-registration. Raw tokens are never logged or persisted to browser storage.

Backend enable flag defaults false. Requires Firebase Admin credentials, project alignment and the partial unique `User.googleUid` index (reviewed `npm run db:indexes`). Frontend reuses public Firebase web configuration; no new client secret. Firebase Console must enable Google and authorize the frontend domain. Real consent and device popup behavior remain deployment checks; mocked provider tests are not proof of live login.

It saves only manually confirmed fields through existing `POST /addresses`; GPS is not reverse-geocoded and precise coordinates are not saved into the address. Real code delivery is only for active users with server-verified email; unknown accounts do not receive mail. Provider failures on this recovery request are intentionally not distinguished from eligibility failures. Proof binds user/authVersion; a later login or credential change requires a fresh proof. Atomic password update/revoke-all; no login token returned. Existing accounts lacking verified email need assisted recovery. Provider/inbox delivery remains unverified while Brevo setup is paused.
- `POST /orders/:orderId/suborders/:suborderId/cancel {version,reason}` →204. Authenticated buyer and owned order only; strict version≥0/reason3–500. Eligible only placed/accepted, before preparation; Razorpay orders require captured/verified paid state. Backend rejects unauthorized403, unrelated404, invalid state/stale version409. Same actor/version/reason replay is idempotent. Stock restored once using committed reservation proof. Captured online cancellation creates one `requested` refund obligation (items plus listed delivery), never bank-credit success. Other shops and original order total stay unchanged. Existing order DTO contains reason/current amount due/refund state. Buyer UI requires explicit acknowledgement and refreshes status after success.
- Admin-only `GET /admin/operations` → `{asOf,thresholds,pendingShops,staleSuborders,payments,refunds}`; each queue `{count,items}` has at most10 oldest samples. Summary is a bounded multi-query read, not a transactional snapshot or SLA assertion. Public/private customer identity, receipt data, API keys and provider payment IDs are excluded. All protected responses private/no-store. Existing workspace links handle actual approval/reconciliation; no auto-action occurs.

## Signed-in account security — 2026-10-30

Added authenticated `POST /auth/password {currentPassword,newPassword}` and `POST /auth/logout-all {currentPassword}` for buyer, seller, delivery and admin. Inputs are strict; passwords follow existing 12–128 character validation, and a new password must differ. No user/role/phone target is accepted. Current-password verification uses the existing password hash; account-security commands share a five-attempt/15-minute account throttle. Incorrect password returns 403 `CURRENT_PASSWORD_INVALID`; concurrent credential changes return 409 `ACCOUNT_CHANGED`; validation returns 400; throttled attempts return 429.

Both return 204 private/no-store and revoke all current sessions including the caller. UI integration must clear the session and require fresh login; neither response returns a new token. Password change/revocation and login serialize through the user document in MongoDB transactions. Internal user/session `authVersion` mismatch invalidates a token independently of TTL/deletion. Missing legacy versions are zero-compatible. No password reset, SMS verification or recovery bypass is implied. Existing login/register/session DTO shapes remain compatible; frontend account controls are not added in this backend-only step.

## Prepaid cancellation/refunds — 2026-10-30

Paid online suborders now support the existing seller cancellation PATCH from `placed|accepted` only, with saved version and buyer-visible reason. The server transaction validates ownership/captured payment, returns that shop's inventory exactly once and creates one refund obligation keyed by suborder ID. Refund amount is the full original shop item subtotal plus its original delivery fee. Clients cannot choose amount, destination or payment ID. Other shops and the original captured total remain unchanged. Cancellation is not a successful refund.

Buyer/seller suborder DTOs add optional `refund {state,amount,updatedAt}`; amount is INR major units. States: `requested|submitting|uncertain|pending|processed|failed`. Provider IDs/account metadata and internal refund proof are not exposed to buyers/sellers. Parent payment state remains `paid` to represent the original captured transaction; refund summaries represent the separate return of funds. A cancelled suborder cannot be prepared/handed over again.

Admin `GET /admin/payments/:orderId/refunds` lists up to 100 shop obligations: `{id,orderId,shopId,shopName,amount,state,testMode,reason,providerRefundId,createdAt,updatedAt,canSubmit,canReconcile}`. Separate backend `RAZORPAY_REFUNDS_ENABLED=false` defaults off; configured original Razorpay account is required. Admin `POST /admin/refunds/:suborderId/reconcile {}` verifies an existing provider refund. All responses are private/no-store and actions are throttled/audited.

Provider submission uses stable suborder UUID `X-Refund-Idempotency` and immutable `{amount:<server paise>,speed:"normal",receipt:<suborder UUID>}`. A short database lease prevents concurrent submissions. Known pending refunds are fetched rather than recreated. Unknown responses remain uncertain; no new key is generated. A separate provider GET verifies refund ID/payment association, amount, INR, receipt and state before processed is recorded. Exact duplicate and out-of-order notifications cannot regress processed or return stock twice. Signed `refund.processed`/`refund.failed` webhooks reuse the raw-body signature/event dedupe boundary and fetch current provider state before applying it. Admin payment details now include a refund section with explicit monetary confirmation, test warnings, retry/status controls and accurate outcome copy. No bank-credit time is promised. Post-preparation returns/disputes, exceptional failed-refund recovery, unobserved external dashboard refunds and unpaid-order closure remain operator workflows. This change does not issue real refunds or enable live checkout/refund flags. See backend `docs/REFUNDS.md`.

## Razorpay online checkout — 2026-10-30

Response: `{orderId,keyId,providerOrderId,amount,currency:"INR",state,testMode,reconciliationRequired,enabled}`. `amount` is integer paise (unlike INR major-unit marketplace DTOs); `keyId` is public, no secret is returned. The frontend persists the attempt key/input before submitting, recovers the same payload after unknown failures, and removes unchanged bag lines only after a server order response. These reserved orders are pending payment, not accepted shop orders.

Standard Checkout returns a callback to buyer-only `POST /payments/razorpay/orders/:id/verify {razorpay_order_id,razorpay_payment_id,razorpay_signature}`. Buyer `POST /payments/razorpay/orders/:id/reconcile {}` fetches provider state when callbacks are missing or uncertain. Every buyer route enforces ownership. Responses are private/no-store and mutations are throttled.

Verified provider capture updates the local payment and order in one MongoDB transaction. Duplicate or out-of-order callbacks cannot decrement stock or regress paid state. A not-yet-visible capture returns a retryable error rather than marking an event processed. Unknown provider mappings also request retry.

Order `paymentMethod` adds `razorpay`, `paymentStatus` adds `paid`, and `onlinePaidAmount` records captured major-unit value. `testMode:true` is persisted for test-key orders and returned to buyer/seller/admin; these are explicitly labelled test orders with no real payment or physical fulfilment. Paid online orders use buyer receipt issuance with `{version,confirmReceived:true}` (no cash acknowledgement) and seller `POST /seller/orders/:orderId/suborders/:subId/complete-handoff {version,code,confirmHandoff:true}`. Existing `complete-cash` rejects online orders. The same expiry/lockout/ownership protections apply, without generating cash records.

Admin-only `POST /admin/payments/:id/reconcile {providerOrderId?:string}` can recover an uncertain creation mapping, but only after fetching the provider order and matching stored amount, INR, account and marketplace receipt. Never invent a provider ID. Pre-preparation prepaid seller cancellation now creates the refund obligation described above; post-preparation returns, settlement/Route, payment abandonment release and disputes remain separate workflows. Modal dismissal never releases stock or switches to COD. Unpaid online stock stays committed for reconciliation. ## Current COD backend contract — 2026-10-30

The COD backend defaults off (`ORDERS_COD_ENABLED=false`). The user-confirmed policy is tax-inclusive product prices, configured seller delivery charge as final, pickup delivery charge zero, and no extra platform charge/promotional discount. This section supersedes earlier draft order payloads below. Live frontend checkout, explicit COD confirmation, persistent retry recovery and owned order history/details are now integrated; activation still requires seller processing and real-browser journey verification. See [live COD integration](LIVE_COD.md).

- Buyer-only `POST /orders` requires an `Idempotency-Key` (16–100 alphanumeric/underscore/hyphen characters) and `{areaId,addressId,addressVersion,paymentMethod:"cod",expectedTotal,items:[{productId,variantId?,qty}],fulfilments:[{shopId,method}]}`. `expectedTotal` is an acceptance comparison, not trusted pricing. Do not send local `acceptedPrice`, shop ownership, stock, roles or payment/order status. The backend recomputes each listing/variant price and fees and commits inventory plus order together.
- A new request returns 201; identical same-key retries return 200 with the original order; changed payload under the same key returns 409. The UI must durably preserve the key/payload while a network outcome is uncertain and must not clear the bag or invent a success on timeout. Only confirmed non-committing validation errors permit a new attempt. A 409 price/address/stock issue requires a fresh review. Replays return original snapshots even if an address/listing later changes.
- Buyer-owned `GET /orders?limit&cursor` and `GET /orders/:id` return `Order`-compatible data with additive `address` snapshot, `paymentStatus:"unpaid"`, and suborder `shopName`/`shopAddress`. Lists use signed newest-first buyer-scoped cursors in exposed headers; the live reader follows complete pagination. Foreign or missing IDs return 404. ### Identifier and relationship invariants

- A **category** has a stable opaque `id` and public unique `slug`. A **subcategory**
  has its own `id`, `slug`, and exactly one `categoryId`; a category cannot be removed
  while approved shops or active listings reference it.
- A **shop** has an immutable `id`, public unique `slug`, and one or more approved
  category/subcategory assignments. Category results must include only shops eligible
  for the requested service area and whose public status is active.
- A **product** is a shop-owned listing: its `id` belongs to exactly one `shopId` and
  one platform category/subcategory. Matching names in two shops never share product,
  stock, price, offer, or variant records.
- A **variant** has an immutable `id` scoped to exactly one `productId`; its price,
  availability and inventory are independent. It is invalid to order a variant without
  its owning product or from a different shop.
- A **cart line** is `{ productId, variantId?: string, qty }`. The browser may derive
  shop identity for grouping, but the server must derive and validate it from the
  product/variant relation. Cart-line identity is `(productId, variantId ?? null)`.
- An **order** has one buyer and one or more **suborders**. Each suborder contains
  exactly one `shopId`, one fulfilment/delivery method, and only line snapshots that
  resolve to that shop. A delivery assignment is attached to one platform-delivery
  suborder, never the aggregate order.
- Delivery method is one of `seller_delivery`, `platform_delivery`, or `pickup` and
  must be allowed by the shop at checkout. Fee and serviceability are server-calculated.
